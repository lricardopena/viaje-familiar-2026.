# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static HTML itinerary for a family road trip: **Adirondacks → Vermont → White Mountains → LEGOLAND New York, August 14–23, 2026**. All UI text and content is in Spanish. There is no backend, no build system, no package manager, and no test suite. Hosted as-is on GitHub Pages.

## Repository structure

- `index.html` — the shell: all HTML, CSS, and JavaScript (rendering logic + pure helper functions). Contains no trip content — it loads `data.js` via a `<script src>` tag and renders from the global `TRIP_DATA` it defines.
- `data.js` — all trip content, as one JS statement: `const TRIP_DATA = { days: [...], activityDests: {...}, hotelDests: {...} };`. This is what you edit for any content change (times, descriptions, hotels, EV charging info, new days). **Edit this file, not `index.html`, for anything that is data rather than behavior.** The value is JSON-shaped (double-quoted keys/strings throughout) even though the file is JS, not JSON — that's what makes it loadable with a plain `<script src>` instead of `fetch()` (see Development workflow).
- **Theme Park Companion** (`assets/theme-park-core.css` + `assets/theme-park-core.js` + `parks/*.js` + one thin HTML shell per park) — a reusable engine for theme-park day companions: progress tracking, dynamic "¿Qué hacemos ahora?" recommendations, an illustrated + geographic (Leaflet/OSM) map viewer with GPS, per-child ride eligibility, and park services (dining/restrooms/first aid/etc.). **Never park-specific logic in `assets/theme-park-core.js`** — it reads everything from a `window.PARK` object that each park's `parks/<id>.js` file defines. `storyland.html` and `legoland.html` are near-identical thin shells (same markup, same `<link>`/`<script>` tags for the core) that differ only in which `parks/*.js` file they load and a couple of placeholder strings overwritten at runtime by `applyParkTheme()`. Adding a new park means writing a new `parks/<id>.js` + a one-line-different HTML shell — not touching the core or copying an existing park's app. Full field-by-field contract documented in the header comment of `assets/theme-park-core.js` and in `specs/architecture/park-contract.md.asc`.
  - `parks/story-land.js` — Story Land's data (migrated 1:1 from the original single-file `storyland.html` implementation — same ids, same `localStorage` key `storyland_state_v1`, same recommendation behavior). Its data-provenance comments (Plus Codes collected on-site, map-marker calibration method, etc.) live here now.
  - `parks/legoland-new-york.js` — LEGOLAND New York Resort's data (added for the 23-ago-2026 day trip). Restriction/POI data was gathered by web research (no direct fetch access to legoland.com from the dev sandbox that built it) — see the file's header comment for full provenance/confidence notes and what still needs on-site/official re-verification before the visit.
- `archive/Viaje_Ago2026_familiar_visual_PIXEL10_v7_Riparius_Lake_George.html` — a frozen backup copy, kept for reference only. Do not edit it, and do not treat it as a source of truth; `index.html` + `data.js` together are canonical.
- `HANDOVER.md.asc` — encrypted (GPG symmetric, AES-256; see root `README.md` for the decrypt command). Trip/business decisions and their context. See "Decisions & specs" below — read before making non-trivial trip-content changes.
- `specs/` — encrypted with the same scheme and password as `HANDOVER.md.asc` (see `specs/README.md` for the full index, unencrypted). Architecture, design and content guardrails, split into thematic documents under `specs/architecture/`, `specs/product/`, `specs/operations/` — the technical sibling of the handover. See "Decisions & specs" below. (`specs/SPECIFICATIONS.md.asc` was the original monolith; it's now a short stub pointing to `specs/README.md`.)
- `README.md` — repo title plus the decrypt instructions for `HANDOVER.md.asc`.

Why split like this: `index.html` (rendering logic, rarely changes) and `data.js` (trip content, changes constantly) used to be one ~40KB file. Nearly every real edit is a content edit, so keeping content in its own file means an edit only needs to touch `data.js` — no need to read or re-send the CSS/JS shell — which keeps content edits cheap. It also means GitHub's diff view for `data.js` changes shows just the changed day, and `index.html` stays stable across almost all commits. Content is a `<script src>`-loaded `.js` file rather than a `.json` file fetched with `fetch()` specifically so that opening `index.html` directly from disk (double-click, `file://`) keeps working with no local server — `fetch()` is blocked cross-origin under `file://`, but a same-directory `<script src>` is not.

## Development workflow

There is no build, lint, or test tooling — open `index.html` directly in a browser (double-click works fine, `data.js` loads via `<script src>`) or serve the directory with any static file server (e.g. `python3 -m http.server`) to preview changes. Verify by loading the page and clicking through days/sections manually.

## Architecture

The page is rendered client-side from a single data structure, `TRIP_DATA` (defined in `data.js`, loaded before the main script runs):

- **`TRIP_DATA.days` array** (one object per day of the trip) is the source of truth. Each entry carries: date/day-of-week, place, emoji, headline `tag`, weather (`wx`), packing list (`pack`), hotel, an `acts` array of `[time, title, description, badge, priority?, waypoints?]` activity tuples, an `ev` block of raw HTML for EV-charging options, and a `maps` array of address strings. The optional 5th tuple element (`priority`) is `'star'` (⭐ IMPERDIBLE) or `'opt'` (◯ OPCIONAL) — see the UI convention documented in `specs/product/itinerary-app.md.asc`. The optional 6th element (`waypoints`) is an array of `{label, addr, tag?}` sub-points for one activity that covers a walkable cluster of nearby named spots (e.g. a town's pedestrian core) — `index.html`'s `wp()` renders them as a collapsible list under the activity card, each with its own independent "🚗 Ir ahora"/📍 navigation to `addr` (not tied to the parent activity's own destination). `tag` on a waypoint reuses the same `'star'`/`'opt'` language. Use this only when several real, individually nameable stops belong to one activity; don't use it to just split an activity's description into bullets.
- **`TRIP_DATA.activityDests`** and **`TRIP_DATA.hotelDests`** are lookup maps (keyed by day number as a string) that supply the Google Maps destination strings used by each activity's/hotel's "🚗 Ir ahora" button — these must stay in sync (by index) with `acts` and `maps` in the corresponding `days` entry.
- `data.js` is formatted with each `days` array element and each lookup-map entry on its own line (rest minified) — this lets you `grep -n '"d": "17"'` (or similar) to jump straight to one day's line instead of reading the whole file.
- In `index.html`, `const {days, activityDests, hotelDests} = TRIP_DATA;` destructures the data at the top of the main script — this only works because `data.js` is loaded via a preceding `<script src>` tag, so `TRIP_DATA` already exists as a global by the time the main script runs.
- A block of small pure functions (`wicon`, `clothes`, `actIcon`, `excite`, `expectation`, `mission`, `story`) derive UI details (icons, an "excitement" meter, kid-facing mission chips, a short narrated summary) from the day's data — they pattern-match on keywords in Spanish strings like `place`, `tag`, and `pack`. When adding a new day or activity, keep vocabulary consistent with the existing keywords these functions check for (e.g. `'coaster'`, `'gondola'`, `'lluvia'`, `'bermuda'`) or they'll silently fall through to generic defaults.
- The rendering code builds the day-selector nav and one `<section class="day">` per entry by string-templating the data into `#nav`/`#days`. There's no framework — all rendering is manual `insertAdjacentHTML`/template literals. This code sits inside a `{ ... }` block (not a function) purely to scope its local variables (`nav`, `root`, `obs`, etc.) away from the top-level script.
- `IMG()` builds a Wikimedia Commons image URL from a bare filename (the `img` field per day); `go()`/`see()` build Google Maps directions/search URLs from an address string.
- Bottom nav (`prevDay`/`nextDay`/`goToday`) and an `IntersectionObserver` keep the sticky day-selector's highlighted button in sync with scroll position. `goToday()` matches against a hardcoded year/month (2026-08), so it only auto-highlights correctly during the actual trip dates. These functions (and `days`/`activityDests`/`hotelDests`) are declared at the top level of the main script, outside the rendering block, since they're wired up via inline `onclick=` in the HTML and must stay in global scope.

## Conventions

- Keep all user-facing copy in Spanish, matching the existing tone (casual, addressed to the family, second person).
- `data.js` is one array/map entry per line (minified within each line, JSON-shaped) — match this style rather than reformatting, to keep diffs small and each day skimmable as one line. `index.html` stays minified/dense as before.
- EV-charging (`ev` field) entries distinguish "✅ principal/alternativa" (fast NACS DC chargers) from "🔌 backup" (slower J1772 Level 2) — preserve this distinction when editing charging info.
- **Residential locations are never stored in this public repo.** When the itinerary needs to represent the family's home, use the logical label `"Home"` in `data.js` (`maps`/`activityDests`/`hotelDests` entries, and Google Maps links as `?destination=Home`) — Google Maps resolves it from whichever account opens the link, so no address, residential city, coordinates, Plus Code, or Place ID for the residence is ever committed. In UI copy, show "🏠 Casa" (or "🏠 Regresar a casa") to the user; the literal string "Home" only needs to appear inside the Maps URL/data value, not in visible text.

## Decisions & specs — where a change gets recorded

Two encrypted document sets track everything that isn't itself the itinerary content: `HANDOVER.md.asc` (root) and the thematic documents under `specs/` (see `specs/README.md` for the full index). Same GPG scheme, same password (symmetric AES-256, not stored in the repo — see either file's `README.md` for the decrypt/re-encrypt commands). They're split by kind of information, not by importance:

- **`HANDOVER.md.asc`** — trip/business decisions: what the family decided and why (destinations, hotels, restaurants, what's optional vs. confirmed, resolved discrepancies, the day-by-day itinerary state, EV strategy *rationale*).
- **`specs/architecture/`, `specs/product/`, `specs/operations/`** — architecture, design and content guardrails: repo/stack conventions, publishing checklist, UI conventions, editorial style rules, and the full technical spec of the Theme Park Companion (`assets/theme-park-core.js` + `parks/*.js`; data model, scoring weights, zone/cooldown logic, per-child eligibility). Start at `specs/README.md` for which document covers which topic.

When you make or learn about a change that should be durable — a new trip decision, a reversed decision, a new architecture/design guardrail, a convention you had to invent on the spot — it belongs in one of these two files, not just in the git commit message or the chat. Classify it the same way the split above does: **is this "what did we decide for the trip" (handover) or "how should the site be built/behave" (specs)?** If genuinely both (rare — see handover section 29/64 for the one existing case, "fuente de verdad"), it's fine to put the precedence rule in the handover and the technical detail in specs.

**Reading `specs/` vs. `HANDOVER.md.asc` follows different rules — see `specs/README.md` for the specs policy in full.** In short: `specs/**/*.md.asc` may be decrypted/read proactively, without asking first, whenever the content is relevant to the task at hand — it's technical documentation needed to work in this repo, not something that requires permission to look at. Use only a passphrase available through a legitimate, authorized channel (never guess, derive, or reuse one from an unrelated context); never print, log, or otherwise expose the passphrase itself; keep decrypted plaintext temporary and delete it before finishing; if there's no legitimate way to access it, say so rather than inventing content. Editing a `specs/` document doesn't require asking first either — update the canonical document when a real decision changes architecture/behavior/guardrails/contract, re-encrypt, verify the roundtrip, delete the plaintext, and avoid duplicating the same rule across documents.

`HANDOVER.md.asc` (trip/business decisions, including sensitive family data) keeps the stricter guardrail: **ask the user whether to decrypt/edit it now or skip it for this session** before doing either. You do not have the passphrase and must not attempt to guess it, derive it, or reuse one seen in unrelated context. Updating it means asking the user to paste the password into the conversation (it lands in that session's chat history — the same tradeoff noted in `HANDOVER.md.asc` section 62), so don't treat it as a routine step to do silently: surface the question, let the user say "skip" or provide the password, and if they skip, just proceed with the rest of the task and mention in your summary what would need recording later (so it isn't silently lost). Never invent content without user input, and never rewrite a section you haven't read — decrypt first, edit, then re-encrypt with the same scheme (`gpg --symmetric --cipher-algo AES256 --armor`), and delete the plaintext copy before finishing.
